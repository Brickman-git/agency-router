# Проверка роутера на задачах агентства

Версия 0.6, 2026-10-01. Это план сравнительного эксперимента; прогоны на реальных пакетах не выполнены. Отдельные короткие пробы навыка промптинга не входят в этот пилот. Цель — проверить качество маршрутов и стоимость полного цикла принятия результата, а не подтвердить заранее выбранных победителей.

## Сначала проверить подключения

Подтвердить вход Codex через ChatGPT, доступность `gpt-6.1-sol` и нужные инструменты. Для каждого запуска фиксировать effort (`high` / `xhigh`), requested/effective service tier, режим оплаты и capabilities. Для медиа подтвердить передачу нужного изображения, аудио или видео через доступный инструмент; не считать один путь к файлу достаточным входом.

Единственная модель — GPT‑6.1 Sol: обычный запуск High, сложный случай XHigh, requested service tier default. Резервной модели нет; неподключённые провайдеры и автоматический платный API-fallback исключены. Учебная серия из шести запусков уже проведена; она не заменяет пакеты ниже.

Не создавать API-ключи или дополнительную оплату ради пилота. Тестовые публикации/письма/бюджетные изменения проверять в fixture, sandbox или штатном предпросмотре; реальные внешние действия требуют соответствующего поручения. Служебные чаты скрытые, один писатель в checkout. Текущий документ сам по себе не запускает серию.

Первая волна — **16 × 2 = 32 запуска исполнителей**. Начать можно с P01–P12 (24 запуска), затем добавить P13–P16. Проверки подключения и оценивание учитывать отдельно. Этот проект заменяет прежнюю общую схему 12 × 4; старые программные fixtures можно использовать для P08/P09 после сверки требований.

## Два вида измерения

**Практическое:** BB + CLI + модель + штатный инструментарий. Это определяет ежедневный маршрут. Одинаковы цель, стартовые данные и приёмка; различия инструментов явно записаны.

**Сравнение режимов одной модели:** одинаковый harness, инструменты, prompts и исходные материалы. Оно проводится через текущий подписочный вход; отдельный платный API автоматически не используется. Различия настроек и реально доступных инструментов фиксируются отдельно.

После первой волны повторять спорные пакеты в High/XHigh в пределах согласованного бюджета. Не менять одновременно CLI, effort и service tier, если нужно установить причину разницы. Один успешный запуск не доказывает статистическое преимущество режима.

## Что записывать

Поля: `package_id`, `task_ids`, `input_hash`, `provider`, `model`, `effort`, `serviceTier_requested`, `serviceTier_effective_or_unknown`, `tool_access`, `started_at`, `finished_at`, `acceptance_pass`, `critical_errors`, `repair_count`, `review_minutes`, `total_minutes`, `quota_before/after_or_unknown`, `artifact_paths`, `limitations`.

Число запросов не равно расходу подписки. Квоты сравнивать относительно собственного окна каждого провайдера; неизвестные оставлять unknown. В полную стоимость включать повторные попытки, чтение результата, ручную редактуру и проверки. Если расход не виден, сравнивать качество/время, не утверждать, что маршрут дешевле по подписке.

Для кода — скрытые пользовательские сценарии; для данных — эталонная разметка; для текстов — факты, обязательные условия и независимая рубрика; для медиа — просмотр конечного файла; для исследования — реестр утверждений и источников. LLM-рецензент не является эталоном. Имена моделей скрыть, порядок ответов менять, спор решать по исходникам/тестам или редактором.

## Как принимать решение

Критическая ошибка запрещает автоматическую приёмку данного класса до разбора. Среди прошедших критерии выбирать меньшее полное время и меньшую подтверждённую нагрузку на подписку. По одному пакету не утверждать статистическую победу модели или равенство семейств; итог — предварительное решение по конкретному классу с указанием числа наблюдений.

P16 отдельно позволяет сравнить одиночного ведущего с разрешённой командой на том же пакете, если такая проверка понадобится. Это дополнительные запуски за пределами основной сметы; фиксировать передачи контекста и работу рецензента. Команда должна дать измеримый выигрыш, а не просто больше текста.

После пилота записать для каждой проверенной задачи: выбранная конфигурация, основание, резерв, критерий пересмотра. Поле `evidence_status` менять только для реально проверенных профилей/задач; один успешный кодовый пример не подтверждает все 128 маршрутов. Перед реализацией диспетчера отдельно протестировать выбор fallback, недоступность выбранной GPT‑6.1 Sol, неизвестную квоту и неподдерживаемый медиа-вход.
