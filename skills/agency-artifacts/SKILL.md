# Стандарт артефактов агентства

Версия навыка 0.1.0; схема метаданных agency-artifact/1.0. Оформляй результат сам, без отдельного агента для проставления полей.

1. Определи формат, назначение и существующий контракт. Прочитай PROJECT.md/project.json выбранного проекта, карточку задачи и профильный контракт. Не выбирай клиента по старой переписке. Метаданные описывают документ, а не заменяют содержательную работу. Не добавляй выдуманные строки raw или содержательные задания ради примера оформления. Visual-plan обычно принадлежит content/копирайтеру: при незаданном решении slots=[] означает pending, а не утверждённый отказ от картинок; пример слота хранится отдельно как template. Количество и расположение определяет редакторский процесс model-task-prompts, не этот навык метаданных.
2. Используй [стандарт](references/standard.md) и [схему](assets/metadata.schema.json). Markdown начинается YAML-блоком между `---`. JSON остаётся строгим JSON и хранит те же поля в `_meta`. YAML перед JSON запрещён. Для JSONL, бинарных файлов, raw-источников и закрытой чужой схемы — отдельный `.meta.json` с `target`, без изменения исходника.
3. Заполни известные project_id, department, task_ref, owner, title и artifact_type. artifact_id сохраняется при обновлении одного логического документа; version растёт при содержательном изменении. Новому артефакту нужен новый ID. Не копируй ID/даты примера как реальные. Неизвестные project/owner/task допускаются в draft с null; ready к ревью требует реальных привязок. scope=template — только настоящая заготовка, не обход обязательных полей клиентского документа.
4. status — состояние документа. task_ref ссылается на задачу BB Tasks или текущий BB thread, если записи Tasks нет. Не дублируй изменяемый статус задачи и не объявляй её завершённой по approved документа. approved допустим только после фактической приёмки с reviewer/decided_at/decision_ref и точной версией. Чужое решение не выдумывать; уже действующее решение использовать в его пределах.
5. Источники и зависимости хранятся в source_refs и depends_on; подробные выгрузки/цитаты — по профильному контракту. Пути от корня проекта, версии явные. При изменении входа сначала impact-review; устаревшее одобрение не переносить на изменённый результат. access=public не разрешает публикацию. Секреты в шапку не писать.
6. Для нового файла можно использовать `python scripts/artifact.py init PATH --format md|json --title TITLE --department DEPARTMENT` и заполнить draft. Скрипт не перезаписывает существующее. Проверить `python scripts/artifact.py validate PATH [PATH ...]`; зависимости — requirements.txt. Валидатор проверяет схему/даты/дубли ключей, не достоверность фактов, доступов и человеческих решений.
7. Сохрани рабочие контракты Reels, Insights, task.json и чужих API. Если `_meta` несовместим со схемой, создать sidecar с target либо использовать существующий manifest. SKILL.md сохраняет собственный front matter name/description; автоматически не добавлять туда эти поля. Массовая миграция старых файлов — отдельная задача.

Выход: оформленный файл, исход проверки, незаполненные обязательные привязки и следующая проверка по задаче. Для поручения/маршрута использовать model-task-prompts; для содержательного текста — профильный навык. Не загружать все навыки ради метаданных.
