# Поручения агентам

Версия 0.3.1: направления проекта, knowledge_refs, передачи и gates. Если рабочая копия показывает 0.1.1, не приписывать ей правила этой версии.

Сначала прочитай [BB-привязки](references/bb-bindings.md) и [контракт](references/contract.md), затем только справку выбранного семейства: [GPT-5.6](references/gpt-5.6.md), [Astra](references/astra.md), [Claude](references/claude.md), [Gemini](references/gemini.md), [Grok](references/grok.md). Это локальные конспекты официальной документации, проверенной 2026-09-13, и отдельно обозначенная политика агентства. При новой версии модели сверяй официальный источник; не переносить специальные рекомендации на другую версию как доказанный факт.

Для первого заказа, отсутствующего PROJECT.md или изменения общего контекста прочитай [паспорт проекта](references/project-passport.md). Он определяет содержание, владельцев и обновления PROJECT.md/project.json. Свободный текст — допустимый старт; отсутствие паспорта не блокирует бриф или разовый ответ в чат.

1. Из запроса и доступного контекста выдели результат, исходники, область разрешённых действий, инструменты, пути и приёмку. Не спрашивай то, что уже известно. Не подменяй подготовку поручения его исполнением.
2. Одна операция — один короткий контракт. Для большого заказа составь контракт оркестратора и отдельные контракты стадий, с входами от предыдущих стадий. Не копируй весь каталог и все справки в каждое задание.
3. Для задач проекта, передачи между ролями или gates прочитай [карту проекта](references/agency-project.md): сначала PROJECT.md/project.json и принятые knowledge_refs, затем папку направления. Для выбора конечного результата используй outcomes и journey_id в assets/agency-operating-model.json; отдельные source_ids описывают похожие практики, не гарантируют доход. Используй `scripts/project-context.js` и `assets/agency-operating-model.json` для шаблона контекста по типу задачи. Общие знания не дублировать; недостающее направлять владельцу. Для нового дизайн-направления проверить разбор конкурентов (обычно пять); для иллюстрации по принятой системе этот gate не нужен.

   Для сохраняемого рабочего документа применяй agency-artifacts: YAML front matter в MD, _meta в JSON, sidecar для raw/закрытой схемы; существующие форматы не ломать. Для файлового задания используй структуру [хранения](references/storage.md). Если проект уже имеет контракт (Insights, Reels, кодовый репозиторий), сохрани его и укажи ссылки. Копии данных вместо существующего источника истины не создавать.
4. Собери JSON по [образцу](assets/task.example.json). В конфигурации BB копируй точные provider/model IDs из BB-привязок; `anthropic`, `google`, `claude-fable-5.1` не являются проверенными IDs этого роутера. requested serviceTier — fast/default, неизвестный effective хранить отдельно. Для черновика допустимы null/пустые входы: явно назови, что надо заполнить. Не придумывай MCP ID, доступность подписки, частотности, бюджет или разрешение публиковать.
5. Скомпилируй через `node <skill-dir>/scripts/compile.cjs <task.json>`: результат в stdout, файлы сам скрипт не меняет. Общий код `prompt-kit.js` используется и страницей роутера. Текст адаптера — краткая подсказка, полную справку в промпт не вклеивать. Поручение может быть отредактировано под задачу с сохранением контракта.
6. Модель, effort и serviceTier задаёт провайдер при запуске, не фраза в промпте. Проверить запрошенную и эффективную конфигурации. Luna: только High/Max и Fast; при недоступности Fast выбрать другую подходящую модель. Это предпочтение владельца, не требование OpenAI. API-параметры не приписывать CLI без проверки поддержки.
7. В контракте 0.2 задать work_context, context_requirements, skills и gates. Gate хранит проверяемые входы/версии, владельца решения, evidence/review-pack и обратный маршрут. Для статьи/полной страницы копирайтер сдаёт текст + visual-plan.json + краткие ТЗ. Число 0…N и desktop/mobile размещение обосновываются задачей читателя, SERP/конкурентами либо редакторским решением; затем review текста и плана. При slots=[] не запускать дизайнера. Передача содержит article/plan revisions, slot IDs, design/requests/<id>/BRIEF.md и ожидаемые asset IDs; финально проверить собранную страницу. Названия слотов, размеры и содержание из примеров считать предложениями до чтения реальной статьи и брифа; не выдавать их за согласованные входы. Не использовать одобрение старой версии для материально изменённого результата. Уже данное действующее поручение сохраняет силу. Production, органические посещения и клиенты — разные результаты; при ожидании внешних данных сохранять next_check_at, не крутить бесконечный цикл.

   Приёмка — наблюдаемые свойства результата, конкретные релевантные проверки. Не требовать раскрыть внутреннюю цепочку рассуждений, повторить полный анализ или запустить агента-критика для любой мелочи. Объяснения, расчёты, источники и краткое обоснование решения допустимы.
8. Выдай готовый промпт, отдельно конфигурацию запуска и незаполненные входы. Если просят аудит: укажи противоречия, лишние инструкции, отсутствующие критерии и исправленную версию. Уважай уже предоставленные полномочия; шаблон не вводит повторных согласований.

Улучшение качества требует испытаний на реальных задачах; наличие шаблона не доказывает превосходство модели. Метод проверки и ограничения — [evaluation.md](references/evaluation.md).
