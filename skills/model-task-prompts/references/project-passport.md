# PROJECT.md: паспорт и навигация проекта

## Назначение и обязательность

`PROJECT.md` — короткая точка входа для человека и нового агента: что за проект, зачем он нужен, кто решает и где искать актуальные материалы. Это не полный бриф, не журнал каждого действия и не копия всех знаний. Обычно достаточно одной-двух страниц.

Для разового ответа в чат паспорт не обязателен. Бриф можно составить из свободного описания: «Нужен сайт стоматологии, цель — заявки». Отсутствующие ответы становятся вопросами; отсутствие самого файла не блокирует работу. Запись созвона, статистику и другие фактические входы описание идеи не заменяет.

Если работа продолжается в выбранной папке проекта и нужен общий контекст, исполнитель создаёт минимальный **черновик** из известных сведений. Не выбирает клиентский проект сам, не требует сначала подготовить все папки и не объявляет неизвестные факты утверждёнными. При существующем README/паспорте использует его либо согласованную карту соответствия; не заводит второй источник истины.

## Что внутри

| Раздел | Содержание |
|---|---|
| Шапка | Метаданные agency-artifact/1.0: стабильный artifact_id, project_id, владелец, версия, статус, даты, task_ref, review |
| Что делаем | Название, продукт/услуга и краткое описание проекта |
| Зачем и для кого | Цель, аудитория, рынок, язык, измеримый результат если уже определён |
| Границы | Что включено в текущий заказ, ограничения и исключения |
| Кто принимает | Владелец проекта и ответственные за конкретные решения; неизвестные роли явно отмечены |
| Текущее положение | Этап, ближайший результат, существенные блокеры; ссылка на настоящую систему задач |
| Где материалы | Ссылки на продукт, бренд/голос, аудиторию, дизайн, SEO, репозиторий, созвоны и отчёты — только существующие или явно pending |
| Решения и вопросы | Ссылки на принятые решения с датой/версией и открытые вопросы, влияющие на следующий шаг |

Не хранить пароли, токены, полные стенограммы, сырые выгрузки, изменяемые цены и подробную канбан-доску. Для них использовать профильный источник и ссылку. Наличие паспорта не означает доступ к сервисам.

## Связь с project.json

`PROJECT.md` объясняет человеку цель, границы и навигацию. `project.json` хранит машинные привязки: project_id, canonical_root, knowledge_refs (путь, версия, статус, владелец), department_roots, systems и existing_contracts. Это дополнительный файл для задач с файловой структурой, не условие обычного диалога.

Машинные пути и knowledge_refs каноничны в `project.json`; бизнес-описание — в паспорте, подробные знания — в профильных документах. В Markdown не копировать весь JSON. Неподтверждённый путь в шаблоне имеет статус template_unverified/pending, а не available. Для закрытой схемы JSON метаданные разместить в sidecar.

## Когда и кто обновляет

| Событие | Действие исполнителя |
|---|---|
| Начало продолжающейся работы в выбранном проекте, когда нужен общий контекст | Создать draft из известного, перечислить неизвестное; не выдумывать согласование |
| Подтверждена новая цель, аудитория, объём, этап или ответственный | Обновить затронутый раздел и ссылку на решение/исходное поручение |
| Создан новый канонический документ либо подтверждён перенос | Обновить knowledge_refs и ссылку в паспорте, проверить существование; не переносить данные ради схемы |
| Закончена обычная задача без изменения общего контекста | Сохранить её результат в направлении и запись в трекере; паспорт не трогать |
| Найден конфликт или неподтверждённое изменение | Сохранить вопрос/предложение с источниками. Не подменять действующее решение догадкой |
| Изменён принятый факт или версия знания | Проверить влияние на зависимые брифы, контент, дизайн и текущие задачи; отметить затронутые результаты для ревью |

Обновляет агент, выполнивший изменение, или назначенный хранитель контекста. Принимает владелец соответствующего решения по действующим полномочиям. Уже данное пользователем поручение не требует повторного разрешения на внесение подтверждённых изменений.

Перед записью перечитать текущую версию и локальные правила. Сохранить чужие изменения. Содержательная правка: тот же artifact_id, version + 1, updated_at, ссылка на основание; прежнее одобрение новой версии не наследуется. Необязательная косметическая правка не означает нового бизнес-решения. Старую принятую версию сохранить через реальную Git/документную историю либо отдельную версию; не обещать автоматическую историю там, где её нет.

## Проверка и передача

Проверить метаданные, разрешение относительных ссылок, совпадение project_id, актуальность путей и версий в JSON, отсутствие секретов и выдуманных утверждений. В передаче указать, какие разделы изменены и почему, кто/что подтверждает основание, какие зависимости требуют внимания. Формальный валидатор не проверяет истинность бизнес-фактов.
